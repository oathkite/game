# 地形履歴の分離保存

RoomSqlSnapshotでRoom snapshot本体と地形op列を分離。射撃で追加されたopだけをseq付きで保存し、移動では既存opを書かない。可変state・追加op・outbox・alarmはRoomの既存transaction内で更新する。再戦時には新しいmatchへ切替し、古いopを消去する。clientへ送る全履歴は読込時に復元するため、ネットワークprotocolは変更しない。

SQLiteのRoom保存形式はversion2。旧version1はそのまま読み、次のbattle更新から移行する。op_count・match_id・連続seq・個数・opの整数座標/半径を確認し、不整合はroom-unrecoverableへ送る。未対応versionは従来どおり拒否する。旧handlerへ戻すと新形式を読めないため、rollbackにはこのreaderを維持する必要がある。単純に旧コードへ戻して継続できるとは扱わない。

## 同じfixtureでの測定

| map | 変更前・操作中snapshot最大 | 分離後の本体最大 | 地形op追加回数 |
| --- | ---: | ---: | ---: |
| moss-valley | 18,942B | 9,811B | 296 / 全296op |
| reed-hills | 17,058B | 8,995B | 262 / 全262op |

測定scriptは各段階のSQLite保存・読込結果と元snapshotを比較し、同じ地形での再保存でop追加が増えないことをassert。ここでのbytesはJSON payloadであり、SQLite journal・index・課金量ではない。地形opそのものの保存容量は別途必要。

- SQLite unit: 移動位置とack更新で本体のみ1書込、旧/新形式読込、transaction rollback、欠損op拒否、再戦resetを確認。
- server全体77件成功（edge専用3件は通常runでskip）、Node/Cloudflare型チェック成功。
- local edgeの試合replaying中SIGKILL→同一match/地形→generation2→重複発射拒否が成功。
- 破損snapshotの隔離と元データ保持、Directory障害→SIGKILL→alarm再送も成功。

まだ全opを読み出して初期surfaceからmaskを復元している。圧縮mask checkpoint＋短い末尾opによる復元は次の実装。報告JSONのrestore p95は従来のBattle JSON復元単体の測定で、新SQL adapterを含む性能ではない。保存量の減少をCPU・費用の同率改善と読み替えない。
