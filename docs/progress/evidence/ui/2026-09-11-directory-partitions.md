# Directoryの地域・mode分割

キーを `v1:{asia|europe|americas}:{custom|1v1|2v2}:0` とし、各組1shardから開始する。クイック割当・一覧要約の更新は対応するDOへ送る。初回の一覧参照も含めて地域のlocationHintを指定するが、実際の配置を保証するものではない。custom部屋作成のUI/API既定は従来どおりasia。

## 一意なコードと並行処理

旧public DOのroom_codesを6桁コードの共通発行元として使う。既発行コードを再利用せず、別区分や既存部屋との衝突を防ぐ。頻繁な要約更新を共通発行元へ送らない。新しい部屋の発行だけは共通元に依存するため、ここが停止すると新規部屋作成は失敗する。既存の部屋への招待・再接続はRoomへ直接届く。

同一区分のallocate/quickはblockConcurrencyWhile内で候補検索・発行・予約を直列化する。別区分は別DO。共通コード発行RPCを待つ区間にはSQL cursorを残さない。1000部屋の保護上限は各区分に適用する。これを実容量の保証としては扱わない。

## 一覧と移行

公開一覧はcustomの3区分と旧publicの最大4ページを取得し、ID順に統合して20件を返す。重複IDはupdatedAtが新しいものを選ぶ。各区分の続きも含めてcursorを返す。旧GET一覧は互換用に最大100件を維持。

旧publicの要約はTTLまで読める。既存Roomは次の要約更新から新しい区分へ書き込む。旧要約の即時移設・削除は行わないため、移行直後は古い状態がTTLまで表示されうる（入室時はRoomで再検証）。旧quick待ち列の予約は移設せず、新しい割当は新しい区分で開始する。既存参加者の部屋と再接続先は変更しない。全体一覧の取得失敗時は部分一覧を成功扱いしない。

## 検証

- キー9通りの一意性、複数ページ統合、20件上限、重複時の最新要約、空一覧をunitで確認。
- local edgeの公開21部屋ページング・同時quick割当と地域/mode分離・再接続の3件成功。
- SQLite保存先をread-onlyで確認し、asia/custom、europe/1v1、europe/2v2、americas/2v2が別DBに保存され、同一DBに複数区分が混在しないことを確認。
- Directory障害→SIGKILL→alarm復元→generation 2再接続の検証が分割後も成功。
- 試合replaying中のSIGKILL→同じ地形・match→重複発射拒否も成功。

実地域RTT、Cloudflare容量・費用、共通コード発行元の負荷、既存公開環境での移行リハーサルは未確認。複数shardへの拡張には割当・列挙・migrationの追加設計が必要で、現在の末尾0を変えるだけでは拡張しない。
