# 7. 技術選定

この章では、採用する技術と monorepo の構成、テストの方針を定める。
選定の軸は「物理コードをサーバーとクライアントで 1 つのパッケージとして共有できること」である。
弾道再計算方式は、この共有が成り立たなければ実現できない。

## 7.1 採用するスタック

| 層 | 選定 | 選定理由 |
|---|---|---|
| 言語 | TypeScript（strict）、pnpm workspace | 物理、地形、プロトコルを 1 つの言語で書き、サーバーとクライアントから同じパッケージを import する |
| 描画 | PixiJS v8 | WebGL/WebGPU の 2D スプライトエンジン。最初は矩形を並べて描き、後でドット絵のスプライトシートに差し替える。地形マスクは 400 × 225 のテクスチャとして持ち、最近傍補間で整数倍に拡大する |
| クライアントの枠 | Vite + React | 設定、ロビー、部屋、リザルトと、対戦中の左右パネルを React で書く。ゲーム画面は PixiJS の Canvas を React から 1 箇所でマウントする。SSR は不要なので Next.js は使わない |
| ゲームサーバー | Node.js + ws | 部屋の生成と破棄、席の予約、切断からの再接続、部屋ごとのタイマーを自前で持つ。[通信プロトコル](./05-protocol.md) は 1 本の WebSocket に全メッセージを載せる設計で、Colyseus の「HTTP でマッチングしてから部屋ごとに接続する」型と噛み合わないため採らない |
| メッセージ検証 | Zod | プロトコルの型とスキーマを共有パッケージに置き、サーバーで全メッセージを検証する |
| ホスティング | サーバーは Fly.io か Railway、クライアントは Cloudflare Pages | 部屋は 5 分以上生きる状態を持つので、常駐プロセスに置く。静的なクライアントは CDN 配信でよい |
| 永続化 | 持たない | 対戦結果やランクを保存したくなった時点で Postgres を足す |
| テスト | Vitest、Playwright | 物理の golden replay を Vitest で、対戦の流れを Playwright で検証する |

Phaser を採らないのは、物理エンジンとシーン管理を抱えているためである。
物理は自前で決定論的に書くので、Phaser の物理は使わず、二重に持つことになる。
PixiJS は描画だけを担うので、この重複が起きない。

サーバーの中身は、時刻と乱数を外から渡す純関数として書く。
部屋の管理と対戦の状態遷移は `(state, command, now) => { effects, wakeAt }` の形で、送るべきメッセージと次に起こす時刻を返す。
WebSocket はこの関数に命令を渡し、返ってきたメッセージを各接続に送るだけの薄い層にする。
この形にしておくと、制限時間切れ、再接続の期限、リザルトの自動クローズ、放置部屋の削除を偽の時計で数ミリ秒のテストにできる。

## 7.2 monorepo の構成

```
packages/
  sim/        物理、地形、風の変化規則、ダメージ、勾配と傾き。外部依存なし。protocol の型だけを参照する
  protocol/   メッセージの型と Zod スキーマ、RoomState と MatchState などのデータモデル
  maps/       マップ定義（折れ線の頂点とスポーン）と、整数演算のマスク生成コード
  engine/     対戦の状態遷移（Loading から Finished）。時刻と乱数を注入する純関数と、時計につなぐ host
apps/
  client/     Vite + React + PixiJS。solo モードでは engine をブラウザ内で動かす
  server/     Node.js + ws。部屋、ロビー、再接続と、engine の橋渡し
  e2e/        Playwright。2 つのブラウザで 1 戦を通す
```

`sim` が中心である。
ここには DOM も Node の API も入れず、`(state, input) => result` の形の純関数だけを置く。
サーバーもクライアントも同じ関数を呼ぶので、[データモデル](./06-data-model.md) の決定論の契約が成り立つ。
`sim` が `protocol` の型とマップの大きさの定数を参照する形にし、逆方向の依存は作らない。
`sim` の風は「前ターンの値と乱数の出目から次の値を求める純関数」で、乱数そのものはサーバーが引いて渡す。

`maps` はマップの形状を折れ線の頂点と板の上下面で持ち、整数の線形補間だけでマスクを生成する。
PNG を持たないのは、画像のデコード結果が環境で異なると初期地形がずれて決定論が壊れるためである。
整数演算だけなら Node とブラウザで同じマスクになり、マスクのチェックサムをテストで固定できる。

`engine` を `server` から分けるのは、client の solo モード（開発順序の 2）がサーバーなしで同じ状態遷移を動かすためである。
サーバーと solo モードは同じ `engine` を呼び、違いは効果を WebSocket に送るかブラウザ内で配るかだけになる。

## 7.3 描画と判定の分離

後からスプライトを載せる前提で、判定と描画を最初から分ける。

- 地形：判定は地形マスク、描画はマスクの各セルを白い正方形として描いたもの。
- 機体：判定は半径 3 セルの円、描画は正方形で組んだ絵を傾きに合わせて回転させたもの。
- 弾：判定は 1 セル、描画は進む向きに回転させた 1 つの正方形と飛行中の尾。

最初の版の描画はセル単位の矩形で済ませる。
PixiJS の Sprite と Texture に差し替えるとき、`sim` のコードには手を触れない。
スプライトシートは Aseprite で 1 ピクセルを 1 セルとして描き、PixiJS の Assets で読み込んで最近傍補間で拡大する。
フォントは最初の版では DotGothic16 だけを Google Fonts から読み込み、数字と英字にも使う。Geist Pixel は配布形態を確認してから足す。

## 7.4 入力の実装

[画面と操作](./03-ui-and-input.md) で定めた入力の統一は、次の実装で行う。

- Pointer Events だけを使い、`mouse*` と `touch*` のイベントは登録しない。
- ゲーム画面のルート要素に `touch-action: none` を指定する。
- パワーの計測は `performance.now()` の差で行い、requestAnimationFrame の回数を数えない。
- pointercancel は長押しの中断とし、射撃を確定しない。

## 7.5 テストの方針

**sim のテスト**が最優先である。

- golden replay：代表的な `TrajectoryInput` と地形から `ShotResult` を記録し、変更のたびに比較する。
- 境界値：仰角 10 と 90、向き左右、傾き -45 度と +45 度、パワー 0 と 100、風 -10 と 10、マップ端への着弾、マップ外への消失。
- 勾配判定：登れる坂、登れない坂、下り、落下。
- クロス環境：同じテストを Node と Playwright のブラウザで実行し、結果が一致することを確認する。

**server のテスト**は、状態遷移と検証を対象にする。

- 無効な `turn.fire`（範囲外、手番でない、歩数超過、勾配違反）が `turn.pass` になる。
- 制限時間切れで自動的にパスになる。
- 切断と再接続で `conn.state` が正しく復元される。
- 再接続の期限切れで切断側の負けになる。

**client のテスト**は、Playwright で 2 つのブラウザを開いて 1 戦を通す e2e を 1 本持つ。
細かい UI の単体テストは、面白さの確認が終わるまで最小にする。

## 7.6 開発の順序

設計を実装に移す順序は、遊びの核を早く確認できる順にする。

1. `sim` の物理と golden replay。ブラウザなしで弾道を数値で確認する。
2. `client` の単体動作。サーバーなしで 1 人で撃って、地形が削れる様子を見る。ここで重力、風、初速の初期値を調整する。
3. `server` の部屋と状態遷移。2 つのブラウザで 1 戦を通す。
4. マップ「谷」で遊び、面白さを確認する。
5. 残り 2 枚のマップと切断まわり。

2 まで進めば「うまいショット」の感触は確認できる。
面白くなければ 3 に進む前に数値と規則を見直す。
